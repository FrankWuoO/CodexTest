The Visitors Tab: UIKit → SwiftUI

A quick guide for the team — what the old UIKit version of the Visitors tab does, what the new SwiftUI version does, why we rewrote it, and how the two are wired together. A single Flagr flag, visitors/implementation, decides which one runs.

Ground rule: the code is the source of truth References point to files & types by name (line numbers move)

1The short version

The headlines first; the details are in the sections below.

One flag flips the whole tab

visitors/implementation = uikit / swiftui. AppMasterWireframe.makeVisitorsWireframe picks one. Default is uikit, so if the flag is off you get the old version unchanged.

Old = "frozen" UIKit

Config is locked in at VisitorsContainerWireframe.init and the tabs are built once. Everything hangs off Storyboards/xibs, the VisitorsManager singleton, and Combine subscriptions.

New = "injectable" SwiftUI

All UI lives in Packages/DesignSystem with no networking code. Data goes through the stateless VisitorsRepository; state is @Observable; navigation/analytics are injected as closures.

Why we rewrote it

The old version is hard to test and change (Storyboard outlets, a forever-living singleton, empty states juggled with isHidden, layout hacks). The new one is built so "remove the old path" is "delete one folder."

The glue lives in one file

VisitorsHostingController is the UIKit↔SwiftUI boundary; SwiftUIVisitorsWireframe is just a thin wrapper around it.

The new version still leans on the old singleton

App-wide counts the singleton owns — the tab badge, the paywall's visitor count, the Picks upsell — plus a few analytics events. The new code recomputes its own counts and .send()s them back so existing consumers keep working (~a dozen references left).

The gotcha: two independent flags

screen_version (grid vs. single-profile feed) and declining_visitors_place (whether the decline UI shows) are independent — but turning on single-profile quietly makes declining_visitors_place do nothing.

⚠️ The easiest thing to misread: two independent flags, and the single-profile no-op

screen_version controls "grid vs. single-profile card feed"; declining_visitors_place controls "whether the decline UI appears." They're independent (any combination is valid) — but the decline UI only exists in the grid path. The single feed's interaction model is swipe-up / skip, so there's no place for the decline UI to live:

5Full config catalog

The Visitors tab is driven by 15 Flagr flags (visitors/*) parsed into VisitorsProperties, plus 4 non-Flagr inputs (gender, premium, review-mode, reskin). The new version folds a handful of them into the immutable Configuration (which has 3 fields); the rest live on the @Observable GridPresentation or are read inside closures. Open each entry for the old vs. new effect.

6API / data layer

Why the new version still touches VisitorsManager (~a dozen references)

Two reasons remain. (1) App-wide counts the singleton still owns: the tab badge, the paywall's visitor_count, and the Picks upsell trigger. The new host recomputes its own counts and then .send()s them back into the singleton's subjects so the existing consumers keep working (a "reverse edge"). One detail: the paywall's likes-you count is now computed locally in the new path, not read from the singleton. (2) A few analytics events still log through VisitorsManager. The references are spread across VisitorsHostingController (+ its +SingleProfile extension) and YouLikedViewController.
Aside: there's no dedicated count endpoint — counts come from each list's total_count, and the aggregate badge is recomputed locally by comparing each visitor's last-seen against the last time the tab was opened.

The UIKit ↔ SwiftUI bridge

  • The host's child: a UIHostingController<Visitors.Screen>.
  • Navigation as closures: CellActions (defined in the package), the profile-detail handler, You-Liked, and the single-profile handlers — all injected from the host.
  • A shared UIKit detail page, sandwiched both ways: BWFFullProfileDetailsVC is a Swift class (not ObjC). The new code wraps it back into SwiftUI via FullProfileDetailsView (a UIViewControllerRepresentable), forming a UIKit → SwiftUI → UIKit sandwich. (The view-controller chain is pure Swift, but the viewer model objects it carries are still ObjC.)
  • The old version's ~5 forward SwiftUI embeds: the filters empty state, the filters footer / empty-response view, the single-profile feed (LikesFeed.HostingView), the photo-verified intro, and the filters sheet.

8Intentional design decisions

A few things in the new version look unusual on purpose. They're choices, not bugs.

The pager doesn't use the native TabView(.page)
SwiftUI's paged TabView mis-lays-out on the very first swipe, so Visitors.PagerView is a custom horizontal paging ScrollView with a SegmentHeader. The reason is written in the file's header comment.
The detail flow keeps the "last selected viewer"
VisitorsDetailContext mirrors a long-standing quirk of the old WhoViewedMeStore: the selected viewer is only ever assigned, never cleared. Copying that is what lets store-dispatched actions (decline / delete) target the right list afterward.
In single-profile mode, the two distance tabs share one filtered list
That single list feeds both feeds (each gets its own card cursor) and is also used only as the source for the badge count — it's never shown as a tab of its own.
Reskin is gone — the reskinned look is now the baseline
After v79 the reskin is no longer a toggle; the geist font, gradient background, pink underline, etc. are unconditional. Any doc that still mentions a reskin flag is out of date.

9Glossary

Things that look one way but are another (the code wins): (1) the CoreDataModels folder name is a historical leftover — there's no Core Data, just an in-memory identity map; (2) BWFFullProfileDetailsVC is a Swift class, not ObjC; (3) the visitors/implementation chain is pure Swift (Flagr → @UserDefault → enum), not an ObjC-backed remote-config value; (4) the grid-vs-feed render switch is in the package's Visitors.Screen (its TabContentView), not in Visitors.Layout; (5) two methods both return isFemale() — showOnlyThoseWhoLikedMeInVisitors() feeds the request's likes_only, while displayVisitorsToUser() drives blur / gating / empty states / analytics. Don't mix them up.
